Make one thing useful.

Write Python or Node, or begin with a template. Name the tool, describe its purpose and declare the packages it needs.

Your logic, not a new framework.
02 / TEST SAVED CODE

Know what comes back.

Save first, then run with JSON inputs. Inspect stdout, stderr, exit status and timing. Retained results are labelled when the code or inputs change.

A test runs the saved tool—not a draft.
03 / DISCOVER

Connect on your terms.

Enable the tool and refresh tools/list in a compatible client. Calls pass a JSON object on stdin and return the script’s printed output.

PWA and theme notes ↗

A clear connection contract

Bring a client.
Check the transport.

Local or cloud model choice belongs to your MCP client. It does not imply a cloud service can reach—or safely expose—OmniForge.

Small, explicit HTTP surface

POST /mcp accepts one JSON-RPC request at a time for initialize, tools/list, tools/call and ping.

This is limited HTTP JSON-RPC, not full Streamable HTTP. There is no OAuth, session tracking or working SSE channel. Third-party client compatibility has not been live-verified; a client must accept this limited transport.

Before you run it

Local control.
Honest boundaries.

For trusted people running trusted code. Not a hosted multi-user service, not a sandbox and not safe for public exposure.

Keep access private

The dashboard and management API are unauthenticated. Anyone who can reach them can read, edit and run tools. Bind locally or restrict access to a trusted LAN. Do not port-forward or expose a public reverse proxy.

A key is not dashboard auth

Set OMNIFORGE_API_KEY to require a Bearer key on POST /mcp. That key does not protect the dashboard, management API or GET /mcp. No OAuth is provided.

Scripts share the container

Scripts inherit the app’s environment, including its MCP key, and can access its writable data and network. Only run trusted scripts and packages. Do not place unrelated secrets in the environment.

Execution and hosting constraints

Runs and dependency installs block the single worker. Output is not capped, per-script memory limits are not enforced and timeouts do not kill descendant processes. There are no CSRF, Origin or Host checks.

Container hardening is not per-script isolation. PWA installation requires HTTPS or localhost; its offline screen cannot execute or save tools. Public-safe hosting and security gaps are not solved by this page.

Image and tags on Docker Hub ↗

Run with local-only access

The shell check below requires your key to be set first. It does not add authentication to the dashboard.

POSIX SHELL
# Set OMNIFORGE_API_KEY to a strong random value first.
: "${OMNIFORGE_API_KEY:?Set a strong random key first}"
export OMNIFORGE_API_KEY
docker run -d --name omniforge \
  -p 127.0.0.1:8000:8000 \
  -e OMNIFORGE_API_KEY \
  -v omniforge_data:/opt/omniforge/data \
  -v omniforge_lib:/opt/omniforge/lib \
  --restart unless-stopped \
  dbzocchi/omniforge:latest

Open http://localhost:8000. Create a tool, save it, then choose Run / Test.

Need LAN access or hardening?

The local bind above intentionally prevents other machines connecting. Review network restrictions, container permissions and resource limits before changing it.
